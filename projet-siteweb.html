Duplication d’un site web sous Docker

Reproduction d’un site existant dans un nouvel environnement technique, avec adaptation de la structure, isolation des services, reconfiguration des conteneurs Docker et mise en place d’une architecture réutilisable pour de futures duplications.

1. Contexte du projet

Ce projet s’inscrit dans un besoin concret de l’entreprise : réutiliser un site web existant comme base de travail pour créer un nouveau site nommé Metiss’Lab. L’objectif n’était pas simplement de copier des fichiers, mais de mettre en place une méthode propre, reproductible et maintenable pour dupliquer un site complet tout en l’intégrant dans une infrastructure déjà en production.

Le site d’origine fonctionnait déjà avec plusieurs composants : un front-end, une API, une base de données MySQL, un accès d’administration via phpMyAdmin et un système de reverse proxy. Le nouveau site devait reprendre la structure de départ, mais être capable de fonctionner avec ses propres données, son propre nom de domaine et ses propres ports, sans interférer avec les autres projets hébergés sur la même machine.

2. Objectif technique

L’objectif principal était donc de créer une duplication fonctionnelle et indépendante d’un site existant, en conservant l’architecture générale tout en adaptant les éléments nécessaires à un nouveau projet. Cette duplication devait permettre :

  • de conserver le fonctionnement du site d’origine ;
  • de créer une nouvelle version sous un autre nom ;
  • de séparer les bases de données pour éviter tout conflit ;
  • de modifier les noms de domaines, ports et identifiants techniques ;
  • de préparer une méthode réutilisable pour d’autres duplications futures.

En pratique, il s’agissait autant d’un projet de duplication applicative que d’un travail d’ingénierie d’infrastructure, car chaque composant devait être reconfiguré avec précision pour fonctionner dans un écosystème partagé.

3. Architecture du projet

L’architecture reposait sur plusieurs briques techniques articulées autour de Docker. Le projet comprenait :

  • un conteneur front-end ;
  • un conteneur API ;
  • une base de données MySQL ;
  • un accès phpMyAdmin ;
  • un reverse proxy avec Nginx Proxy Manager.

Tous ces services devaient cohabiter sur la même machine et la même adresse IP locale, aux côtés d’autres projets déjà déployés. Cela imposait une vigilance particulière sur les noms de conteneurs, les ports exposés, les noms de domaines et les liens entre services.

4. Duplication des fichiers et préparation de l’environnement

La première étape a consisté à se connecter en SSH au serveur afin de créer une nouvelle arborescence de travail pour le site dupliqué. Un dossier dédié a été créé pour le nouveau projet, puis seuls les éléments réellement nécessaires ont été copiés depuis le site original :

  • le dossier lerelais-api pour la partie back-end ;
  • le dossier lerelais-front pour la partie front-end ;
  • le fichier docker-compose.yml décrivant les services.

Les fichiers générés automatiquement ou les dossiers inutiles au déploiement n’ont pas été repris. Ce choix permettait de repartir sur une base propre et de limiter les risques de conflit avec les données ou configurations du projet d’origine. 5. Adaptation du fichier Docker Compose

Le cœur du projet a été l’adaptation du fichier docker-compose.yml. Ce fichier décrit les différents services à lancer, leurs dépendances, les variables d’environnement, les ports et les volumes.

Plusieurs modifications ont été nécessaires :

  • renommer les services et les conteneurs ;
  • changer les variables de nom de domaine ;
  • adapter le nom de la base de données ;
  • réaffecter les ports exposés ;
  • corriger les dépendances entre services.

Cette étape était indispensable pour éviter qu’un conteneur du nouveau projet interfère avec ceux du projet d’origine, notamment dans un contexte où plusieurs sites partageaient déjà la même IP.

6. Duplication et adaptation de la base de données

Pour que le nouveau site dispose de ses propres données, il a été nécessaire de dupliquer la base de données existante. Une nouvelle base a été créée, puis le contenu de la base d’origine y a été importé grâce à un export / import MySQL.

Cette approche a permis de conserver exactement la même structure fonctionnelle que le site original, tout en isolant complètement les données du nouveau projet. Ainsi, toute modification faite sur le site dupliqué n’avait aucun impact sur le site source.

Le lien de connexion à la base a ensuite été ajusté dans l’API afin de pointer vers la nouvelle base créée pour le projet. Ce point était essentiel pour garantir l’indépendance de l’application.

7. Modification du front-end et des fichiers applicatifs

Au niveau du front-end, plusieurs fichiers ont dû être modifiés afin que le nouveau site soit techniquement distinct du site source. Cela concernait notamment :

  • le nom du site dans l’onglet navigateur ;
  • les fichiers HTML, CSS et JavaScript générés ;
  • l’identifiant principal utilisé par le JavaScript ;
  • les noms de domaines appelés dans le code.

L’objectif était d’éviter que les deux sites partagent des ressources ambiguës, par exemple au niveau du chargement des fichiers ou du rendu de la page après rechargement. Sans cette adaptation, il existait un risque que le navigateur ou l’environnement aille chercher le contenu du mauvais site.

8. Mise en place du reverse proxy et intégration réseau

Une fois les conteneurs prêts, il a fallu permettre un accès propre au site via son nom de domaine. Pour cela, Nginx Proxy Manager a été utilisé comme reverse proxy.

Son rôle était d’associer chaque nom de domaine au bon service en fonction du port correspondant. Cela permettait à plusieurs sites de coexister sur une même machine tout en étant accessibles par des noms différents.

En complément, une redirection DNS a également été configurée dans pfSense afin que les noms de domaines pointent correctement vers l’adresse IP locale du serveur. Cette étape était indispensable pour rendre la solution réellement opérationnelle.

9. Déploiement et tests

Une fois l’ensemble des fichiers et configurations adaptés, les conteneurs ont été lancés avec une commande de build et de démarrage Docker Compose. Cette étape a permis de recréer l’ensemble de l’environnement applicatif dans sa nouvelle version.

Des tests ont ensuite été réalisés pour vérifier :

  • le démarrage correct des conteneurs ;
  • l’accessibilité du site via son nom de domaine ;
  • la connexion correcte à la base de données ;
  • la séparation fonctionnelle entre le site d’origine et le site dupliqué.

Une fois ces vérifications effectuées, le site dupliqué était pleinement opérationnel et pouvait être utilisé comme nouvelle base de travail pour le projet Metiss’Lab.

10. Résultats et compétences mobilisées

Ce projet a permis de concevoir une méthode de duplication fiable d’un site web existant dans un environnement conteneurisé. La solution obtenue est à la fois réutilisable, maintenable et adaptée à un contexte de cohabitation entre plusieurs projets sur une même infrastructure.

Il m’a permis de développer et consolider des compétences en :

  • administration Linux ;
  • déploiement Docker et Docker Compose ;
  • gestion de bases de données MySQL ;
  • configuration réseau et reverse proxy ;
  • lecture et adaptation de fichiers de configuration ;
  • raisonnement d’architecture applicative.

Plus globalement, ce projet m’a permis de comprendre comment déployer une application web complète dans un environnement réaliste, en tenant compte à la fois des contraintes logicielles, réseau et organisationnelles.
